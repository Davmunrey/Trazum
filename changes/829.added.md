**Staging and production for the web app, a `next` channel on npm, and the three GitHub Environments stated in the repository.** (#829)
- *The web app.* Every merge to main is built by Vercel as a staged production deployment: "Auto-assign Custom Production Domains" is off on the Vercel project, so the build serves its own address until it is promoted, and promotion does not rebuild it. `.github/workflows/promote-web.yml` is the button: started by hand from main, under the `production` environment and its reviewer, it runs `scripts/promote-web.mjs`, which reads the deployment from Vercel's API and refuses anything but a ready, staged production build of the project (a preview would be rebuilt with production variables), then promotes it and waits until Vercel says the job succeeded. `rollback` puts production back on a build that served it before. After a rollback Vercel turns automatic assignment off, and the next promotion turns it back on; the job warns when that happens. The Vercel token, project id and team id are secrets of the `production` environment and nowhere in the repository; the token goes to `api.vercel.com` and to no other host. `docs/setup.md`, "Staging and production", has the flow, why a staged deployment and not a custom environment, how to roll back, and the Vercel pages it rests on, each with the date it was read.
- *npm.* A version `X.Y.Z-next.N` publishes to the `next` dist-tag and never to `latest`. `scripts/npm-channel.mjs` decides the channel in `release.yml`'s `decide` job and refuses a prerelease on main, a tag that does not name the manifests' version, and any other prerelease word. Every upload passes `--tag` from that answer; `npm-serves.mjs` waits on the same tag and fails at once if `latest` names a prerelease; the GitHub release, the attached files and the MCP registry listing run for `latest` only. `prepare-release.mjs 3.1.0-next.1` moves the lockstep versions and nothing else, and the tests that hold a document to the current version read the release on `latest` on a next's tree (`recordedVersion`). `docs/releasing.md`, "A next prerelease", is the procedure: a branch, a tag, never a merge.
- *Environments.* `.github/environments.json` states `staging`, `production` and `release`, each with a required reviewer, the branches that may use it and the names of its secrets. `npm run environments` compares GitHub with it and `npm run environments -- apply --yes` writes it, the way `npm run ruleset` does for the branch; the weekly `Repository settings` run compares and never writes. No job runs under `staging` yet: Vercel's Git integration builds it.
- *Tests.* `npm-channel.test.js`, `web-promotion.test.js` and `environments.test.js`. Planted one at a time and put back, each caught by the test named: listed on the pull request.
